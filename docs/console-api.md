# Console API — the brain side

The wire contract every console client builds against: the terminal (`protean ctl`), a native client, an MCP plug-in if one is built. The framing is frozen; the thinking sessions changed operations and fields inside it, never the framing. Code: `src/protean/graph/console.py`; executable form: `tests/protean/test_console.py` and `tests/protean/test_think.py`.

## Finding and reaching the brain

- One console per live session, served by a thread inside `protean think` / `protean resume`. No live brain, no console.
- Listens on `127.0.0.1` only, on an ephemeral port. Never another interface.
- `brain/protean/state/current` names the current session (a new `protean think` or a `protean resume <session>` moves it). `brain/protean/state/<task>/console.json` (mode 0600, removed when the brain exits) holds `{"host": "127.0.0.1", "port": N, "token": "...", "pid": N, "task": "<task>"}`, `<task>` being the session's id. No sandbox the brain runs a child under can read this file: the editor's, a check command's (code the editor wrote, run at grading) and the reader's profiles deny it by name and by the private temp names it is written through, and deny the root's `state/lobby.json` the same way (§ The lobby).
- Every request carries `Authorization: Bearer <token>`. Without it, or with any other value: `401 {"ok": false, "error": "unauthorized"}`, and nothing changes.
- HTTP/1.0, one request per connection. Bodies are one JSON object, at most 64 KiB.

## Endpoints

| Method | Path | Body | Success |
|---|---|---|---|
| GET | `/snapshot` | none | `200` the snapshot |
| GET | `/stream` | none | `200`, `application/x-ndjson`: line 1 is `{"snapshot": {...}}`, then every `log.jsonl` line appended after the snapshot's `log_bytes` and every `transcript.jsonl` line appended after its `transcript_bytes`, verbatim, one per line (each file in its own order), until the run ends; the last line before EOF is one more `{"snapshot": {...}}`, the terminal state (`terminal` set), since `/snapshot` stops answering as the brain closes. `GET /stream?offsets=1` (capability `stream_offsets`) sends the same snapshot lines and every other line as its history entry (§ Stream offsets); any other query is the plain stream |
| GET | `/history?source=log\|transcript[&before=B\|&after=A][&limit=N]` | none | `200` one bounded page of the session's `log.jsonl` or `transcript.jsonl` (capability `history`; § History) |
| GET | `/file?branch=<ref>&path=<path>` | none (both query values percent-encoded) | `200`, `application/octet-stream`, `Content-Length`: the committed bytes of one document in the snapshot's `artifacts`, read from the workspace's object store at the branch's tip (never the working tree, never a clone's `.git`), byte-identical. Only a `branch` the artifacts list with a `path` in its `paths` is served; anything else, `..` included, is `404` (the confinement is list membership, never a filesystem walk); a listed entry that is not a regular file is `404` (a symlink, a submodule or a tree — the mode is checked first, only `100644`/`100755` is served). Missing or empty `branch` or `path`, or a repeated `branch` or `path` key: `400`; any method but GET: `405`; over 25165824 bytes (24 MiB, the console's own bound, the lobby's too; the grader's file bound is a separate 262144): `413 {"ok": false, "error": "<path> is over the 25165824-byte bound"}`. Errors are JSON as everywhere |
| POST | `/pause` | `{}` | holds at the next tick boundary; the call in flight finishes |
| POST | `/resume` | `{}` | releases a pause |
| POST | `/stop` | `{}` | answered first, then the Ctrl-C path: the call in flight books its spend, the session saves, the brain exits 130 |
| POST | `/close` | `{}` | ends the session for good (2026-10-20): every open question is superseded, held work is dropped, the record is `stopped` with `stop_reason` `closed` and stays readable; then stop's path out — the call in flight books its spend, the brain exits 11. Every later operation and `protean resume` are refused (`409`). Offline, `protean ctl close` closes a parked session in `task.json` |
| POST | `/think` | `{"text": "...", "decide": false, "request_id": "..."}` (`decide` may be left out: false; `request_id` may be left out, § Request ids) | appended to the thoughts; with `decide: true` also the operator's decision |
| POST | `/answer` | `{"id": "q1", "text": "...", "request_id": "..."}` (`request_id` may be left out, § Request ids) | closes that one open question |
| POST | `/extend` | `{"usd": 1.5}`, `{"ticks": 5}` or both | widens the session's ceilings; its dollars raise the allowance |
| POST | `/mode` | `{"mode": "auto"}` or `{"mode": "hold"}` | sets the mode, persisted |
| POST | `/approve` | `{}` | releases the one progression held in `hold` |

An operation answers `200 {"ok": true, "event": {...}}` with the event it logged, or `{"ok": false, "error": "..."}` with: `400` malformed body or field (a `think` without a non-empty `text`, or with a `decide` that is not `true` or `false`, and a malformed `request_id`, included), `401` no token, `404` no such endpoint or question id, `405` wrong method, `409` the session's state refuses it, `413` body or text too large, `500` the record could not be saved (nothing landed; the error names why). A think or an answer that repeats an accepted `request_id` answers `200 {"ok": true, "event": <the original event>, "replayed": true}` (§ Request ids). An operation that landed in `task.json` but whose log event could not be written gets no reply: the connection closes, so its delivery is unknown, never refused or failed (§ Request ids says how a think or an answer with a `request_id` is settled).

`409` cases: a `request_id` the session already accepted for another operation or payload (`request_id <id> was used for another operation`); the session was closed or abandoned, or the record ended `done` (runs 1–6 only); `pause` while paused, `resume` while not paused; an `answer` to a question that is not open; an `answer` to a `cap_hit` question (only `extend` releases it); an `answer` to a `reader_cap` question other than `yes` or `no`; an `answer` other than `yes` to an `unknown_spend` or a `no_progress` question; `mode` naming the mode already in force; `approve` with nothing held, or with the held progression already approved; any operation while the run is ending.

## Operations land in state

Each operation is checked, recorded in `task.json`, and logged with `actor: "console"`. The loop acts on it at the tick boundary; no operation reaches a node.

- **think** — the thinker's every later message carries every thought, in order (`"thoughts": [...]`), beside the thought record; it reads each as direction, an answer, a possibility or a decision, and the latest wins on conflict. A think ends a wait for a thought (`awaiting_thought` false) and reaches the thinker at its next call; units already in the session run first. A think that lands while a thinker call runs is in no message yet: when that call's move is an `ideas` or a `rest`, the session does not wait for another thought, and the next call carries it. A think changes no ceiling and starts nothing about money. With `"decide": true` it is also the operator's decision: in the same save, live or offline, `decided` gains their text verbatim (as the thought holds it), its time and the think's index. That is the only way an entry enters `decided`; the thinker never writes it, and a reply that carries it is a decode error.
- **answer** — binds to one id, once. The thinker's own question (an `ask` move) is answered in its next message's `answer`, once. A runtime question's answer stays with the runtime, which acts on it, and never reaches the thinker.
- **extend** — adds dollars and/or ticks to the session's ceilings, live, with no upper wall; its dollars raise the allowance by as much. Each press logs its amount, the resulting ceilings and the resulting allowance. It never changes a per-call cap. It releases an open `cap_hit` question and lifts a ceiling stop it clears, spend that reached the allowance included. It is the only operation that changes a ceiling; besides it, only active work grows the allowance (`accrued_usd`), by that rule.
- **mode** — `auto` (default; a record without the field loads as `auto`): the session progresses on its own unless paused. `hold`: exactly three progressions wait at the tick boundary for `approve` — dispatching a `task` move's plan (its units stay outside the session until released), a retry attempt (attempt 2 or later), and an explore (before its worker call). The accepted-ref move (`integrated`) and the thinker's own call are never held. Switching to `auto` releases whatever is held (`approved` with `by: "mode"`).
- **approve** — releases exactly the one held progression (`approved` with `by: "approve"`): a plan's units enter the session, the retry runs, or the explore runs.
- **think while something is held** — returns it to the thinker (`returned`, with a `to_director` note) and the thinker moves again with every thought: a held plan is dropped and none of its units enter the session; a held explore never runs; a held retry does not run and its unit becomes `failed` as it stands (its work comes back as a new task, smaller, or an explore of what stopped it). A think wins over an `approve` the loop has not yet acted on.

## Waits and the unattended park

An open question, a pause, a ceiling stop, a progression held for `approve`, or a wait for a thought (after an `ideas` or a `rest` move) holds the loop at the tick boundary. A wait is not a tick: nothing is spent while it lasts, and it adds no active time.

While a client holds `/stream` open, the brain waits indefinitely. With none attached, every wait but a pause fires one macOS notification. If no client attaches within the unattended timeout (30 minutes, the session's default), the brain parks: a question, a held progression or a wait for a thought leaves the session `interrupted` (exit 12; the held one stays in `task.json`), and a ceiling stop leaves it `stopped` (exit 11). `protean resume` continues the session. A pause never parks.

## No live brain

`protean ctl answer`, `think`, `extend`, `mode` and `approve` write straight into the parked session's `task.json` (their events carry `"live": false`); `protean resume` then continues. A think or an answer landed this way follows § Request ids when its body names a `request_id` (the terminal client names none): a replay returns the original event and writes nothing. `pause`, `resume` and `stop` need a live brain and are refused. `protean resume --extend N|$X` is kept as a thin alias: one `extend`, then resume.

Terminal client: `protean ctl pause | resume | stop | think <text> [--decide] | answer <id> <text> | extend <N|$X>... | mode auto|hold | approve | snapshot | watch`, each on the current session. `watch` prints the snapshot, then the stream, and counts as an attached client. `protean think "<thought>" [--workspace <clone>] [--mode auto|hold] [--project <name>]` starts a session (default `auto`; in `hold` even its first `task` move's plan waits for `approve`); with no `--workspace` its tree is a fresh git repository with one empty commit under `brain/protean/workspaces/<session>/`. A new `protean think` while another session is parked (awaiting a thought, or interrupted on a question) is not refused: `current` moves to the new session and the old one stays as it was; a live brain (its lock held) refuses a second, and refuses a `protean resume` of another session. `protean resume [<session>]` wakes the named session, which becomes the current one, or the current one when none is named; `--abandon` closes it for good. `protean run` is no verb any more (nonzero exit, as any unknown verb). `protean status` prints the thought record (the thought, standing, open, decided and the moves), the units, the thoughts, the budget, the mode and what is held.

## The editor's transcript

The editor is launched with `claude -p --output-format stream-json --verbose` (the CLI refuses `stream-json` without `--verbose`); the thinker keeps `--output-format json`. Its stdout is read line by line as it runs, a task unit's and an explore's alike, and each line is appended to `state/<task>/transcript.jsonl` as one `transcript` event, which the stream carries during the call. The transcript is a console field only: it is never in `task.json`, the log or a thinker message, and nothing in it counts toward a verdict. The receipt is the stream's final `result` event (cost, usage, session, subtype, result), read the way the single `json` blob was.

## Capabilities and older clients

Every snapshot (`/snapshot`, each snapshot line of the stream, the lobby's `/session`) carries `capabilities`, a list of strings. This brain lists `request_id`, `history`, `stream_offsets` and `walk`. The lobby's `/sessions` carries its own top-level `capabilities`, which lists `history`. A client uses a field or a route that a capability names only when the list names it. An absent list means none. A client ignores a string it does not know. Every field and route below is optional and additive.

What an older client sees: the snapshot and the events have more keys, and it ignores them (`capabilities`; `walk` in `doing`, in `fired`, and on the `call`, `launch` and `fired` events; `request_id` on a thought, and on a `think` or `answer` event, only when a client named the request). The plain `/stream` sends the same bytes as before. A client that sends no `request_id` gets the behavior it got before: two equal thoughts are two thoughts, and a retry is a second operation. `log_bytes` and `transcript_bytes` stop at the end of the last complete line, which is the file's size whenever no line is half written.

## Request ids

A client may name a `think` (a pick is a `think`) or an `answer` with a `request_id`, so that a retry after a lost reply is safe. No other operation takes one; on any other operation the key is ignored, as an unknown key always is.

- `request_id` is an optional body key: 1 to 64 characters from `[A-Za-z0-9_-]`. Any other value, `null` included, is a `400`, and nothing changes.
- The payload identity is the operation plus its fields as received, compared exactly as JSON (`true` is not `1`; text is never trimmed for it): a think's `text` and `decide` (absent reads as `false`), an answer's `id` and `text`. Other body keys are not part of it. The body is never changed.
- On the first `200`, the save that lands the operation also adds `{request_id, op, payload, event}` to the session's ledger in `task.json` (`requests`), so the ledger entry exists before the reply. The logged event and the reply's event carry `request_id`, and a think's thought carries it too (snapshot `thoughts[].request_id`).
- A known id with the same operation and payload answers `200 {"ok": true, "event": <the original event>, "replayed": true}`. Nothing is saved, logged or changed, and the loop is not woken. This check runs before every state check: a replayed answer to a question that is now closed, or a replay on a closed session, still gets its original event, and an answer is never released twice.
- A known id with another operation or another payload answers `409 {"ok": false, "error": "request_id <id> was used for another operation"}`, and nothing changes.
- A refusal or a failure is never kept: the id stays free. A save that fails is a `500` and never a `200`, and nothing landed: the rename of `task.json` is the save's one commit point. `thought.md` is written just before it, so after a failed save it can show the operation the record does not hold; it is a view, never read back, and the next save rewrites it. The id is scoped to the session. The offline path (`protean ctl` with no live brain: `loop.offline_op`, then `console.apply`) follows the same rules: a replay returns the original event and writes nothing, and another payload is refused.
- When the operation landed in `task.json` but its log append failed, the console sends no reply (the client's delivery is unknown) and the loop acts on the operation. A replay of the same request then writes the missing log event once, the ledger's original event, found in the log by `request_id` and operation, never by text, and only then answers `200` with `replayed: true`. Nothing is applied again. The console also writes every missing event of the ledger when it next serves the session (a restart), before it answers anything. The log line of a repaired event has the time it was written, so it can follow later lines. While the log still cannot be written, a replay gets no reply either and changes nothing. A replay or a serve with every event already logged writes nothing. Offline, the same failure is an error that says the operation landed, and an offline replay writes the missing event. An operation sent without a `request_id` has no repair: its record is in `task.json` and its log line is missing.

## History

`GET /history?source=log|transcript[&before=B|&after=A][&limit=N]` (capability `history`) reads one bounded page of the live session's `state/<task>/log.jsonl` or `state/<task>/transcript.jsonl`. The lobby's `GET /history?task=<id>&source=…` reads the same page for any session whose record loads, live or not (§ The lobby).

```json
{"ok": true, "task": "<id>", "source": "log", "size": 131230, "from": 40960, "to": 131230,
 "older": true, "newer": false,
 "lines": [{"offset": 40960, "bytes": 212, "line": {"ts": "…", "event": "answer"}},
           {"offset": 41172, "bytes": 90001, "omitted": "over_line_bound"},
           {"offset": 131173, "bytes": 57, "raw": "<not a JSON object>"}]}
```

- A line's identity is (session, source, `offset`). `offset` and `bytes` count raw encoded bytes, the newline included, never characters.
- `size` is the end of the last complete line at read time. A partial last line is never served.
- Entries are contiguous: `offset + bytes` is the next entry's `offset`, so `[from, to)` is covered whole. `older` means `from > 0`; `newer` means `to < size`.
- No cursor returns the newest page, which ends at `size`. `after=A` reads forward from A. `before=B` returns the page that ends at B. `after=size` gives an empty page; `before=size` gives the newest page, as no cursor does.
- `limit` is 1 to 500, default 200. The whole response body of a page, as sent (JSON with every non-ASCII character escaped, so `é` takes 6 bytes, an emoji 12 and a byte that is not UTF-8 6, the page's own keys included), is at most 262144 bytes. Each entry is charged its encoded size. A page read forward ends before the first entry that would not fit, and a page read backward starts after it, so that entry opens the next page. A page still holds one entry when any line is in range.
- A row that is a JSON object is `line`, whole, with every field kept. Any other row (not JSON, a JSON value that is not an object, a blank line, bytes that are not UTF-8) is `raw`, its text (bytes that are not UTF-8 decoded with replacement characters). A line over 65536 bytes (its newline aside) is `{"offset", "bytes", "omitted": "over_line_bound"}` with its true length, and it still moves the page on. A line whose entry alone would put a page over 262144 bytes (in practice a `raw` row of control characters or bytes that are not UTF-8) is `{"offset", "bytes", "omitted": "over_payload_bound"}` with its true offset and length, and it moves the page on too. No byte range is dropped without a marker. `over_payload_bound` is a newer value than `over_line_bound`: a client treats any `omitted` value it does not know as an omitted line of that length.
- The brain reads in chunks of at most 65536 bytes and never loads a whole file to serve a page.
- `400`: `source` missing or other than `log` or `transcript`, both cursors, a repeated key, a key the route does not take, a cursor that is not a whole number of ASCII digits, a cursor inside a line, or a `limit` out of range. `409 {"ok": false, "error": "offset <n> is past the end of <source> (<size> bytes)"}`: the client marks that span unavailable (the files are append-only, so this means a cursor from another file, or a file that was cut). `404` when the file is a link or not a regular file. `405` for a method other than GET; `401` without the token. An absent file is `200` with `size` 0 and no lines.
- Only `state/<task>/log.jsonl` or `state/<task>/transcript.jsonl` is read, through the brain root, never through a link. No path parameter exists.

Answer history is the log's `question` and `answer` events, read through `/history`; the snapshot does not change. A client says "earlier answers not loaded" until its pages reach `from` 0.

## Stream offsets

`GET /stream?offsets=1` (capability `stream_offsets`) sends the snapshot lines unchanged. Every other line arrives as `{"source": "log"|"transcript", "offset": N, "bytes": n, "line": {…}}`, or with `raw` or `omitted` in place of `line`, exactly as `/history` gives the same line, with `source` added. The exceptions are content bounds, never identity: every line keeps the same `offset` and `bytes` on the stream as on a page.

- A line that a page marks `over_payload_bound`: the stream has no page bound and sends it whole.
- A transcript line: the stream sends it whole up to 16777216 bytes (its newline aside), so the usage a live call reports reaches the client, while `/history` still omits a line over 65536 bytes as `over_line_bound`. A client keeps its own bound for the history it retains. A log line keeps the 65536-byte bound on the stream, as on a page.
- A line whose envelope, as sent (JSON with every non-ASCII character escaped) and with its newline, would pass 16711680 bytes (16 MiB less one 64 KiB read, so a client that reads lines of at most 16 MiB can always read it), or a transcript line over 16777216 bytes: `{"source", "offset", "bytes", "omitted": "over_stream_bound"}` with its true offset and length. A Unicode line under the source bound can pass the wire bound, since escapes are not source length. A client shows the omission; it never drops it.

`over_stream_bound` is a newer `omitted` value; a client treats any value it does not know as an omitted line of that length. The stream reads on from the snapshot's `log_bytes` and `transcript_bytes`, so its offsets are the identity `/history` uses: a client fills a gap with `after=` and drops a line it already holds by (source, offset). A blank line arrives too, as `raw`. The plain `/stream` does not change.

## Walks

Each walk of a tick (one `run_tick`) gets an opaque `walk` id, unique within the session. It is on the tick's `fired` (snapshot `fired.walk`, the `fired` event), on each call the walk opens (`Call.walk`: snapshot `doing.walk`, the `call` event) and on each `launch` event. `tick`, `task.tick` and every ceiling keep their meaning. A walk that an interruption cuts before its save counts no tick, so it and the walk that runs that tick again share `tick` and differ in `walk`; the cut walk logs no `fired`, and its calls keep its `walk`. A client groups a tick's lines by `walk` when it is present, and by `tick` when it is not.

## Branch admission

A `task` move's unit whose predicates carry `parents` proposes a branch: those accepted predicates hand their promise to the unit's children. Before the unit enters the session, inside the same tick, the brain makes one fresh `reader` call (seat `reader`, its own `call` event, charged to the session, capped at `reader_call_usd`) and logs `branch_admitted` or `branch_refused`. Only a reader `yes` admits; a `no`, or any call that fails, answers anything else refuses, and the whole plan goes back to the thinker as one line (`unit 'u-3': branch refused by the reader: <note>`). A reader call that reaches its dollar cap refuses nothing on its own: it is asked once more under twice `reader_call_usd` (clipped by the allowance; the retry's `call` event carries `retry_of`), and if that call reaches its cap too the plan is held unadmitted on a `reader_cap` question — `answer yes` asks again under the wider cap, `answer no` refuses as a `cap_hit` refusal did before (2026-10-18). A reader call that times out or leaves no receipt refuses nothing: its cap is booked, paid work holds on an `unknown_spend` question, and the plan is `held` unadmitted; `yes` releases it and the reader is asked again. The thinker never sees the reader's input, transcript or receipt. Admission is decided once per plan, by the mode its thinker call started in: from `auto` inside the call, from `hold` after `approve` (an admitted plan is `approved`, a refused one is dropped). A branching plan whose call started in `hold` is `held` for its admission even when `auto` landed during the call (released with `by: "mode"` once admitted); a plan admitted inside its call is never asked again, whatever the mode became. A held plan is released only after the ceilings: at a ceiling, or under the call floor (also between two of its admission calls), it stays held and approved, nothing is refused, until `extend`; a think that lands during its admission call returns it (`returned`) and none of its units enter. The parents stay in the re-check set until the branching unit is integrated (`branch_accepted`), except on that unit's own candidate: once every child passes there, the parents of those children are not graded and its `verdict` records each as `excused` with the `children` that carry it, so the unit may rename or remove what they pinned and no parent is a `broke` there (any other accepted predicate is re-checked as always). A child that fails rejects the candidate on its own grade and the parents hold untouched; nothing about a branch asks the operator.

## The weakening check

Every retained `command` predicate names `protected` paths: the files and directories that control its result (its tests, their config), relative to the tree; a directory covers everything under it (`tests` covers `tests/test_x.py`, never `tests_old.py`). A plan whose retained command names none, or names one outside the tree, goes back to the thinker at decode; a delivery-only command may omit them. Before a candidate integrates, and only once it has passed every free check (its own grade, the re-checks, the clean clone), the gate diffs it against the accepted tip it branched from (renames count as a deletion and an addition). The protected set is the union over every integrated unit's command still in the re-check set, less the parents excused on this candidate; the candidate's own commands never count. No protected path touched: no call, and the `verdict` records `weakening` with `result: "untouched"`. Touched: exactly one fresh `reader` call (seat `reader`, its own `call` event, charged to the session, capped at `reader_call_usd`) in a clone at the candidate, given the unit's intent, the touched paths, the accepted commands they control and their hunks (cut at 16,000 characters with a marker), and one `weakening` event. The reader answers `{"verdict": "yes"|"no", "kind": "<kind>", "note": "<one line>"}`, `yes` meaning weakened, kind one of `deleted tests`, `weakened assertions`, `skipped or expected-fail`, `legitimate refactor`, `strengthened`, `unrelated`. `no` integrates as usual. `yes` rejects the attempt like a failed predicate (no integration, the attempt consumed, `failed` after the last): the next attempt's findings carry the touched paths, the kind and the note as evidence. A call that gives no verdict (floor, sandbox, clone, timeout, no receipt, error, cap hit, malformed answer) never integrates: the attempt is rejected with the note `weakening check could not run: <why>`. Since 2026-10-18 a reader that reaches its dollar cap rejects nothing on its own: one re-ask under twice `reader_call_usd`, then the attempt is HELD — neither graded nor rejected, its attempt count unchanged — on a `reader_cap` question (`answer yes` re-asks under the wider cap; `answer no` rejects the attempt as `unchecked` with reason `cap_hit`, exactly as before; `extend` alone does not release it). Nothing about the verdict asks the operator; a timeout or missing receipt does hold paid work on an `unknown_spend` question before the retry.

## Questions

A question in `task.json` (and in the snapshot) has these fields:

- `id`: `q1`, `q2`, and so on, never reused.
- `asker`: `director` (the thinker's seat) or `runtime`.
- `reason`: `question` for the thinker (its `ask` move); `invalid_plan`, `no_progress`, `stale_tip`, `cap_hit`, `unknown_spend` or `reader_cap` for the runtime. `invalid_plan` opens when the thinker's reply was invalid twice. `no_progress` opens when a second reply in a row left the standing unchanged (the first went back to the thinker as a `no_progress` note): no paid call starts until `answer <id> yes`, which calls the thinker again; any other answer is refused (`409`), and a thought that lands meanwhile rides in that call while the answer never does. Money opens no question: spend that reaches the allowance (`ceilings.allowance_usd`) is the `ceiling` stop (`terminal` `stopped`, `stop_reason` `max_usd: …`), set in the same save that books the thinker's, a worker's or an explore's call that reached it (a reader's call is booked in the gate's own save, and the stop follows before any further call), and before a call would start with less than the $0.50 call floor left: no paid call starts until `extend` adds dollars, or the session's own active time, counted at the end of the tick that reached it, clears it (`released`). `unknown_spend` opens in the same save that books any call ending without a receipt (timed out, no receipt, interrupted by Ctrl-C or `stop`, or lost to a kill): its reserved cap is charged, `actual_usd` is `"UNKNOWN"`, and no paid call starts until `answer <id> yes` (before it, only a kill held). `reader_cap` opens when a reader call (branch admission or the weakening check) reached its dollar cap twice: a first cap hit is no verdict, so the same brief is asked once more under twice `reader_call_usd` (clipped by what the allowance has left, as every call is; its `call` event carries `retry_of`, the call it asks again) and that verdict applies; a second cap hit, or no room under the $0.50 call floor for the wider call, opens the question in the same save that books the call. The attempt is held un-graded (its unit keeps its status and attempt count, and no `verdict` or `weakening` event is logged), or the plan is held unadmitted (not refused, not returned to the thinker); its text names the unit, the check, both caps and what the reader has cost on the check so far. Only `yes` or `no` answers it (anything else is refused, `409`), and `extend` alone never releases it: `yes` asks the reader once more under the wider cap, and its verdict grades the attempt or admits or refuses the branch (a cap hit there opens a new `reader_cap`); `no` takes the cap hit's own path, the attempt rejected `unchecked` with reason `cap_hit` (`weakening check could not run: the reader call reached its $X cap`) and the branch refused with reason `cap_hit`, its line to the thinker. A `think` that returns a held plan supersedes its `reader_cap` (`returned`).
- `text`, `created`, `status` (`open`, `answered`, `superseded`), `answer`.
- `actor`: who answered (`console`).
- `disposition`: what the runtime did. `delivered` for the thinker's; `continued`, `extended` or `retried` for the runtime, and for a `reader_cap` `reasked` (`yes`), `rejected` (`no` on a weakening check) or `refused` (`no` on an admission); `abandoned`, `repaired` or `returned` when superseded. A record of runs 1–6 loads read-only and may carry reasons and dispositions this page no longer lists.
- `context`: what the runtime acts on, such as the call ids or the unit a stale tip names. A `reader_cap`'s is `reader_cap` {`check` (`weakening`, `admission`), `unit`, `note` (the last cap hit's), `calls` (every reader call on the check so far), `cost_usd` (their charges), and for a weakening check `attempt`, `accepted_tip`, `candidate`, `protected`, `touched`, `checks` and the held attempt's `worker`, `grade`, `recheck`, `excused`}, plus `settled` once the runtime acted on the answer.

## The lobby

A standing console for the brain root, not for one session: a client lists the sessions, reads one with no brain running, reads its documents, and starts or wakes one. Code: `src/protean/graph/lobby.py`; executable form: `tests/protean/test_lobby.py`.

- `protean lobby` (`--brain` as every verb) serves it: one process that never calls a model and spends nothing, until SIGINT or SIGTERM, which close it (exit 0). It prints `lobby served on <root>`, then `lobby: state/lobby.json`.
- Listens on `127.0.0.1` only, on an ephemeral port. `brain/protean/state/lobby.json` (mode 0600, written whole by rename, removed at exit while it still carries this lobby's token) holds `{"host": "127.0.0.1", "port": N, "token": "...", "pid": N}`, with no `task`. Its token starts and resumes paid sessions, so the editor's, a check command's and the reader's sandbox profiles deny reading it, by name and by its private temp names, as they deny the task's `console.json`.
- The framing is the console's: every request carries `Authorization: Bearer <token>`, and without it, or with any other value, `401 {"ok": false, "error": "unauthorized"}` and nothing happens (no spawn, no file); HTTP/1.0, one request per connection; bodies one JSON object, at most 64 KiB; errors `{"ok": false, "error": "..."}`. An unknown path is `404`; a known path under another method is `405`.
- A session is live exactly when its `state/<task>/console.json` exists, the pid it names is alive (signal 0 reaches it, or the process belongs to another user), and the session's lock `state/<task>/lock` is held (a brain holds it for its whole drive, console included, and the kernel drops it with the process, so a reused pid never keeps a dead session live). The lock is probed only behind a live pid; a lock the probe cannot open (a directory, a permission error) is neither live nor not live: `/sessions` skips that session and echoes it on the lobby's stdout, once until it lists again (as it skips a record that does not load), while `/session` on that session, and `/start` / `/resume` while any session's lock is unprobeable, which must not guess, answer `500 {"ok": false, "error": "session <task>: its lock cannot be probed: <why>"}`; the lobby serves on. A session id is one path component: anything with `/`, and `.` or `..`, names no session (`404`).

A start or a resume spawns exactly one detached brain on the lobby's own interpreter: `<python> -m protean.cli --brain <root> think --project <project> --mode <mode> [--workspace <path>] -- <thought>` (the options first, then `--`, then the thought, so a thought that starts with `-` is a thought and never the child's option), or `<python> -m protean.cli --brain <root> resume <id>`. It runs in its own process session, its stdin closed, its stdout and stderr in a new `state/lobby/launch-<UTC>.log`, with the lobby's environment plus `PYTHONUNBUFFERED=1` and the lobby's working directory; the lobby's token is in neither its argv nor its environment. The lobby polls every 0.2 s for up to 15 s, takes one start or resume at a time, and the brain it spawned is then a session like any other, reached through its own `console.json`. The operator sending the thought is the go: the lobby spends nothing, and the session spends as `protean think` does.
